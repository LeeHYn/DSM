# AI CONTROL SYSTEM v5.1 프로젝트 통합 설계

- 날짜: 2026-08-15
- 대상: `C:\DEV\.ai\system_prompt.md`
- 상태: 2026-08-15 written spec 사용자 승인 완료
- 선택 방식: 기존 프로젝트 전용 규칙 보존 + 첨부 v5.1 호환 규칙 선별 통합

## 1. 목적

현재 `AI CONTROL SYSTEM v3.0`에 첨부된 `v5.1 (Strict Architecture Edition)`의 개선점을 반영하되, 이 프로젝트에서 이미 더 구체적으로 발전한 memory routing, 오류 해결 플레이북, 역할 기반 서브에이전트 계약과 적대적 검증 워크플로를 삭제하거나 약화하지 않는다.

완성된 문서는 이름을 `AI CONTROL SYSTEM v5.1 (DSM Project Adapted Edition)`으로 바꾼다. 단순한 원문 병합이 아니라 현재 프로젝트의 실제 파일 구조와 승인 경계에 맞춘 하나의 일관된 운영 계약으로 만든다.

## 2. 입력 근거와 우선순위

통합은 다음 근거를 사용한다.

1. 현재 `C:\DEV\.ai\system_prompt.md`
2. 첨부된 `AI CONTROL SYSTEM v5.1 (Strict Architecture Edition)`
3. `C:\DEV\.ai\memory\README.md`와 활성 memory 3파일
4. `C:\DEV\.ai\agents\README.md` 및 현재 시스템 프롬프트에 이미 포함된 역할·감사 계약
5. 실제 프로젝트 구조와 현재 Git 상태

상충 시 다음 원칙을 적용한다.

- 플랫폼·시스템·개발자·사용자 지침은 프로젝트 프롬프트보다 우선한다.
- 프로젝트 내부에서는 더 구체적이고 현재 파일 구조와 일치하는 기존 규칙을 유지한다.
- 첨부 v5.1의 일반 규칙은 기존 규칙을 강화할 때만 채택한다.
- 같은 의도를 가진 규칙을 두 벌로 남기지 않고 한 위치에 통합한다.

## 3. 범위

### 포함

- 문서 제목과 버전 표기 갱신
- 한국어·logging·memory 동기화 규칙 강화
- 검증 가능한 목표와 단순성 우선 원칙
- 구조적 설계의 사용자 선협의와 제한된 자율 판단 경계
- 서브에이전트 실행 프로파일 제안 규칙
- memory 위생·컨텍스트 복구 규칙
- 회귀 방지, 완료 보고, 다음 작업 제안과 커밋 메시지 규칙
- Windows 11, Docker와 긴 PowerShell 명령에 대한 프로젝트 조건부 규칙

### 제외

- `DSM_Back/**`, `DSM_Front/**`, `learning-site/**` 제품·산출물 변경
- 새로운 `.ai/memory/memory.md` 생성
- 새로운 `.ai/archive/` 체계 강제 도입 또는 기존 backup 이동·삭제
- 기존 역할 문서나 audit ledger 변경
- 의존성 설치, 네트워크, DB·Docker·Firebase 실행
- Git stage·commit·push

## 4. 통합 구조

### 4.1 언어와 기록

문서 최상단에 `0. CRITICAL: 언어와 기록`을 추가한다.

- 답변과 보고는 상위 지침이 허용하는 범위에서 한국어로 작성한다.
- 코드·설정·프로젝트 변경 뒤 최종 보고 전에 관련 활성 memory를 동기화한다.
- 동기화하지 못하면 완료로 주장하지 않고 누락 이유와 남은 작업을 보고한다.

이 규칙은 현재 7절의 한국어 소통 규칙과 중복되지 않도록 7절에는 표현 방식만 남긴다.

### 4.2 정체성과 의사결정

현재 “시니어 개발자 어시스턴트”를 “시니어 개발자이자 PM 어시스턴트”로 확장한다.

- 직관보다 `.ai/` 문서와 실제 소스·테스트·Git diff·현재 검증 출력을 우선한다.
- 더 단순한 해결책이 있으면 근거와 trade-off를 제시한다.
- 구현 세부 선택은 best practice가 명확하고 승인 범위 안일 때 자율 결정할 수 있다.
- 아키텍처, 데이터 모델, 디렉터리 구조, 핵심 기술 스택처럼 구조를 바꾸는 결정은 선택지와 trade-off를 먼저 제시하고 승인받는다.

“자율 판단”은 기존 수동 승인 gate를 우회할 권한이 아니며, 승인된 설계 안의 구현 세부에만 적용한다.

### 4.3 memory 모델

현재 프로젝트 모델을 유지한다.

| 역할 | 유지할 파일 | 읽기 시점 |
|---|---|---|
| 목표·승인·기술 계약 | `.ai/memory/plan.md` | 모든 작업 시작·종료 |
| 현재 구현·환경·구조 지도·위험 | `.ai/memory/context.md` | 모든 작업 시작·종료 |
| 공정 상태 | `.ai/memory/checklist.md` | 모든 작업 시작·종료 |
| 검증된 오류 해결 지식 | `.ai/memory/error-resolution-playbook.md` | 오류 조사·진단·수정 시 |

첨부 원문의 `memory.md` 역할은 이미 더 엄격한 `error-resolution-playbook.md`가 담당하므로 새 파일을 만들지 않는다. `context.md`에는 현재 구조 지도와 주요 흐름을 유지하되, 모든 파일을 나열해 다시 비대하게 만들지 않고 상세 구조 문서에 연결하는 압축된 지도 방식을 허용한다.

### 4.4 memory 위생

현재 `.ai/memory/README.md`의 routing을 우선한다.

- 활성 3파일은 현재 상태, 활성·대기 목표, 재발 방지에 필요한 계약 중심으로 유지한다.
- 완료 이력이 본문을 압도하면 사용자 승인과 exact writable allowlist를 먼저 확보한 뒤 압축한다.
- `*.original.md`와 `*.failed-*`는 기존 복구 경계를 그대로 유지한다.
- 첨부 원문의 `.ai/archive/<날짜>/`는 기존 backup 정책과 충돌하므로 자동 도입하지 않는다. 향후 archive가 필요하면 별도 설계·승인을 받는다.
- 압축 전후 정보 보존과 UTF-8을 검증한다.

### 4.5 실행 흐름

기존 STEP 1~5를 유지하면서 다음을 명확히 한다.

1. 활성 memory 확인과 실제 상태 대조
2. 오류 작업이면 플레이북 검색
3. 목표를 검증 가능한 milestone로 분해하고 plan·checklist에 기록
4. 구조적 결정과 exact writable allowlist를 설명하고 사용자 승인 대기
5. 승인 범위에서 한 단계당 1~2개 파일을 외과적으로 수정
6. 비례적인 검증과 필요 시 독립 검토 수행
7. 최종 보고 전에 관련 memory 동기화

문서 오탈자처럼 동작과 구조를 바꾸지 않는 수정에도 현재 프로젝트의 계획·승인 규칙은 유지하되, 검증은 변경 위험에 비례하도록 한다.

### 4.6 서브에이전트 실행 프로파일

기존 3.1 역할 계약과 exact writable allowlist를 유지하고 아래 내용을 추가한다.

- 런타임 상위 지침 또는 사용자가 서브에이전트 사용을 허용한 경우에만 후보를 평가한다.
- 단순·짧은 작업은 주 에이전트가 수행한다.
- 위임 이점이 분명하면 실제 지원되는 모델·reasoning effort만 확인해 제안한다.
- 성공 기준을 만족하는 가장 낮은 충분 수준을 권장한다.
- 승인 요청에는 milestone, 실행 주체, objective, exact writable allowlist, forbidden scope, verification, done condition, 모델, effort, 선택 근거, 품질·비용·지연 trade-off, 역할 수, 병렬 여부와 승인된 대체 프로파일을 포함한다.
- 승인된 모델·effort가 실패하면 사전 승인된 대체 프로파일 외에는 임의 변경하지 않는다.

기존 역할 문서, Context Compiler, change-gate와 audit 독립성 규칙은 그대로 유지한다.

### 4.7 기술·회귀 방지 규칙

기존 관례·안정성·보안·side effect 분석에 다음을 추가한다.

- 필요한 최소 구현만 작성하고 요구하지 않은 추상화·리팩터링을 금지한다.
- 확인되지 않은 DB·API·도메인 규약을 추측해 validation이나 제약을 추가하지 않는다.
- 한 도메인의 경로를 수정하면 실제로 같은 계약을 공유하는 형제 경로를 점검한다. 점검은 무조건 수정한다는 뜻이 아니며 영향 유무를 확인하는 것이다.
- 코드나 동작을 바꾸는 변경에는 재현 가능한 회귀 검증을 동반한다. 문서 전용 변경은 Markdown·링크·형식·내용 일관성 검증으로 대체한다.
- DB를 사용하는 현재 DSM 로컬 환경은 Docker와 `127.0.0.1` 바인딩을 유지한다. 이 규칙을 DB가 없는 작업에 억지로 적용하지 않는다.
- PowerShell에서 500바이트 이상이거나 quoting·분기·반복이 복잡한 재사용 명령은 `.ai/scripts/*.ps1`로 작성한 뒤 실행한다. 단순 read-only 조사 명령은 위험과 가독성을 기준으로 판단한다.

### 4.8 완료 보고와 커밋

기존 CCTV 기록과 셀프 체크를 보존하면서 다음 필드를 명확히 한다.

- 수정·추가·삭제 파일 목록
- 관련 `.ai/memory/` 동기화 여부
- 요청과 직접 연결되지 않은 변경 여부
- 실행한 검증과 미실행 검증
- 남은 위험과 승인 gate
- `checklist.md`의 실제 미완료·진행 중 항목에 근거한 다음 작업 1~2개 제안

커밋 메시지는 Conventional Commits 스타일의 명확한 유형과 변경 대상을 사용한다. 제목만으로 이유가 불분명하면 본문에 이유와 영향 범위를 적는다. Git write는 항상 현재 승인 범위 안에서만 수행한다.

### 4.9 컨텍스트 복구

대화가 초기화됐거나 “이어서 작업해” 요청을 받으면 활성 memory 3파일을 읽고 실제 소스·Git 상태와 대조한다. 오류 작업이면 플레이북도 검색한다. 이후 현재 위치, 불일치, 다음 검증 가능한 행동과 승인 gate를 보고한다.

복구 파일인 `*.original.md`와 `*.failed-*`는 명시적인 복구·감사 승인 없이는 읽지 않는다.

## 5. 오류·충돌 처리

- 첨부 v5.1 규칙이 현재 파일 구조와 맞지 않으면 현재 구조에 맞게 번역하고 원문 파일명을 그대로 추가하지 않는다.
- 두 규칙의 강도가 다르면 더 구체적이고 안전한 현재 규칙을 유지한다.
- 상위 런타임 정책과 프로젝트 프롬프트가 충돌하면 상위 정책을 따르고 그 사실을 보고한다.
- 기존 dirty 변경과 수정 대상이 겹치면 덮어쓰지 않고 현재 diff를 기준으로 최소 patch를 만든다.
- Markdown 구조나 링크가 깨지면 완료로 처리하지 않는다.

## 6. 구현 경계

구현은 written spec 사용자 승인과 상세 구현 계획 승인 뒤 다음 순서로 진행한다.

1. `docs/superpowers/plans/2026-08-15-ai-control-system-v5-1-integration.md` 작성
2. `.ai/system_prompt.md` 단일 파일 통합
3. 문서 구조·중복·충돌·경로·UTF-8·whitespace 검증
4. `.ai/memory/plan.md`, `.ai/memory/checklist.md` 종료 동기화
5. 운영 맥락이 실제로 바뀐 경우에만 별도 승인 단계로 `.ai/memory/context.md` 갱신

제품 소스, 역할 문서, audit ledger와 기존 backup은 수정하지 않는다.

## 7. 검증 기준

- 제목이 `v5.1 (DSM Project Adapted Edition)`인지 확인한다.
- 기존 오류 플레이북, backup 경계, 서브에이전트 역할 계약, Context Compiler와 적대적 검증 규칙이 보존됐는지 확인한다.
- `memory.md`와 자동 `.ai/archive/` 도입 문구가 없는지 확인한다.
- 채택 항목이 해당 절에 한 번만 존재하며 상충되는 승인·자율 실행 문구가 없는지 확인한다.
- 경로가 실제 프로젝트 구조와 일치하는지 확인한다.
- Markdown heading·list·code fence, UTF-8, trailing whitespace와 `git diff --check`를 확인한다.
- `git diff --name-only`로 승인된 파일 외 변경이 새로 생기지 않았는지 확인한다.

## 8. 완료 조건

- written spec과 상세 구현 계획이 사용자 승인을 받는다.
- `.ai/system_prompt.md`에 승인 설계가 빠짐없이 반영된다.
- 기존 프로젝트 전용 안전 규칙이 손실되지 않는다.
- 모든 정적 검증이 통과하고 미실행 검증과 남은 위험이 보고된다.
- 관련 활성 memory가 최종 상태와 일치한다.
- Git write는 별도 승인 없이 수행되지 않는다.
